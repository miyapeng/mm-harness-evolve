# Harness 自进化流程：31 篇文献核对与本项目讨论依据

核对日期：2026-09-09。状态：文献方法审查，未改变项目算法，未复现这些论文的实验。适用议题：Q1–Q5。

**主要判断：共同骨架已经清楚，具体搜索与检验策略尚未统一。** 与本项目最接近的路线是冻结模型，读取跨任务执行证据，修改可复用 harness，通过真实重跑选择并保留版本。不同论文在修改对象、证据权限、搜索拓扑和评判信号上仍有显著分歧，不能把它们合成一个“业界标准算法”。

本报告逐项覆盖用户提供的 31 个标题，优先核对原始论文的方法 / 算法部分；对固定框架、立场和评测论文，只作相关性判定。编号保持原清单顺序。链接固定本次读取版本，作者与提交元数据见 [来源索引](harness-evolution-sources-2026-09-09.json)。正文是中文转述，流程比较与项目建议为本次分析，不是论文作者共同提出的结论。没有在本轮核验各论文代码与论文算法完全一致，也没有用不同任务上的分数直接排名。

## 1. 先分清在“进化”什么

| 路线 | 更新对象与时间 | 与第一阶段的关系 |
|---|---|---|
| 离线可复用 harness 搜索 | 用开发任务轨迹修改 prompt、工具、上下文或运行代码，再部署 | 主线：Meta-Harness、AutoSaddler、Self-Harness、SHAPER 等 |
| 测试时 / 任务内适配 | 已经看到当前测试任务或其输出，再改工作流并继续求解 | TTHE、RHI 等；回答当前任务适应，不直接证明未来任务迁移 |
| 无标签 harness 搜索 | 没有官方正确性反馈，以偏好、健康状态等代理选择 | RHO 等；需要另证代理与真实效果的关系 |
| 权重共同进化 | 修改 harness 的同时或交替训练策略 | WHALE、HASE、HarnessForge 等；第二阶段 |
| 外部世界 / 工作区更新 | 改训练环境、任务内模拟器或外部知识 | EnvHarness、Workspace；优化对象需另界定 |
| 固定框架与优化器评测 | 设计执行流程或评价优化器，不提出持久自改循环 | MUSE、VeRO、Priority Ranking 等，保留相关点但不充当算法 baseline |

冻结权重的自动优化不一定是“同模型自我改进”。A＝B、独立会话、固定 B 外层是本项目的实验条件，应逐项核对，不能由标题中的 self 推断。

## 2. 最相关方法的流程差异

| 方法 | 谁 / 什么提出修改 | 证据如何进入 | 怎样搜索和保留 |
|---|---|---|---|
| Meta-Harness | 一个可读文件和改代码的 proposer | 按需查询完整档案 | 多候选与历史版本搜索 |
| AutoSaddler | 诊断与补丁同会话，另有复盘及演化阶段 | 成败轨迹、代码、版本经验 | 同批筛选、开发验证、历史组件复用 |
| Self-Harness | 同模型产生有限候选 | 失败签名、成功参照、历史修改 | 两组比较，限制退化后接纳 |
| SHAPER | 文本梯度驱动的 skill / context 优化器 | 视觉诊断先压成文本 | 先 skill 后 context，beam 选择 |
| AutoDesign | 分析 / 规划后编辑组件 | 跨任务设计轨迹与评价 | 每轮一组件，单当前版本 |
| HarnessLens | 经验驱动的单提案演化 | 轨迹证据与行为关联 | 相关任务验证后再确认 |
| DREvo | 历史经验引导的 proposer | 重新加权的历史 diff 与反馈 | 利用、避免、复测、探索 |
| COMFYCLAW | 工作流修复与 skill 更新 | 区域视觉错误、成败模式 | 合成新提示比较新旧 skill |

出处和适用限制见下方同名条目。这些差异对应不同成本和研究问题，没有足够证据证明“角色越多越好”或“候选越少越好”。

尤其要拆开四个量：**修改者数量、修改者的工具 / 模型调用次数、候选数量、验证层数**。一个修改者可以查多次图、编辑多个文件、提出两个候选；这仍然可以是结构简单的单修改者流程。反过来，一次 HTTP 调用也可能塞入许多复杂指令，却没有查证能力。

## 3. 按用户清单逐篇核对

### 1. GEPA

类型：离线 prompt 搜索。核对位置：§3、Algorithms 1–2。

**流程：** 维护候选池及逐任务分数，按 Pareto 覆盖选择父版本；选一个模块，在小批轨迹与反馈上反思改写 prompt。先做匹配小批比较，有改善再在搜索验证集评估入池；可组合互补候选，最后选版本测试。

**边界与启发：** 原始主要对象是模块 prompt；不能直接等同于任意运行代码进化。 [原文 2507.19457v2](https://arxiv.org/abs/2507.19457v2)

### 2. Meta-Harness

类型：离线代码搜索。核对位置：§3。

**流程：** 一个 coding-agent proposer 按需查询历史源码、分数和轨迹，选择父版本并生成候选；接口检查后运行搜索任务，结果和代码写回档案，反复搜索，最后评估选定版本。

**边界与启发：** 主动查证和历史档案很相关；单个 proposer 可以生成多个候选，并不要求固定单线。 [原文 2603.28052v1](https://arxiv.org/abs/2603.28052v1)

### 3. AutoHarness

类型：离线代码合成。核对位置：§3–4.1。

**流程：** 围绕游戏动作合法性构建代码候选树，用 Thompson sampling 选择节点；环境执行给出非法动作或代码错误，critic 反馈给 refiner 修正代码，继续测试，直到达到目标或预算。

**边界与启发：** 主要合成动作校验、过滤或策略代码；目标和反馈比通用多模态长任务窄。 [原文 2603.03329v1](https://arxiv.org/abs/2603.03329v1)

### 4. MUSE

类型：固定 harness；不列入进化主线。核对位置：§3。

**流程：** 组合视觉感知、任务表达、工具和验证，利用反馈修订当前任务产物。

**边界与启发：** 核对的方法未建立跨任务自动修改并保留 harness 的外循环。产物修订不等于 harness 进化。 [原文 2606.03005v1](https://arxiv.org/abs/2606.03005v1)

### 5. Self-Evolving Embodied Agents via Skill-Harness Evolution（SHAPER）

类型：离线多模态 skill / 上下文进化。核对位置：§3–4.1。

**流程：** 动作前后图像与行动输入逐步视觉诊断，再形成 episode 文本总结与 textual gradient；优化器结合当前版本和历史修改。先进化 skill，再固定 skill 进化 build_context 代码；通过验证保留 beam 中较好版本。

**边界与启发：** 视觉 judge 看图，优化器主要接收文本梯度；规划模型与动作执行组件分开，不能直接假定全系统 A＝B。 [原文 2608.11350v1](https://arxiv.org/abs/2608.11350v1)

### 6. AutoSaddler

类型：离线持久代码更新。核对位置：§4。

**流程：** Diagnosis–Patch 同一会话检查成功、失败与源码并修改；同批重跑严格改善后进入开发验证。Reflection 对比修复、退化、仍失败、仍成功并记录经验；Evolution 利用历史版本和组件继续构建版本，最终选择测试。

**边界与启发：** 三阶段会话不等于多个修改者投票。论文算法、公开 V2 工程和本项目 plugin 必须分别辨认。 [原文 2608.23041v1](https://arxiv.org/abs/2608.23041v1)

### 7. Self-Harness

类型：离线同模型进化。核对位置：§3、Algorithm 1。

**流程：** 把验证器反馈整理成失败签名，结合通过案例和历史修改；同模型提出 K 个最小候选，分别运行 held-in / held-out。两侧均不降、至少一侧提高才接纳，随后合并被接纳修改。

**边界与启发：** 反复用于接纳的 held-out 实质是开发验证；其 proposer 使用当前进化 harness，与本项目固定 B 外层不同。 [原文 2606.09498v3](https://arxiv.org/abs/2606.09498v3)

### 8. EvoHarness-RL

类型：训练运行协调策略。核对位置：§2。

**流程：** 让模型学习交替使用环境工具和 track、commit、recall、note 等外部状态工具；SFT 后进行成本感知 GRPO，配合经验库整理。

**边界与启发：** 主要训练何时管理运行状态，并非冻结模型后自由生成代码补丁。 [原文 2608.05446v1](https://arxiv.org/abs/2608.05446v1)

### 9. WHALE

类型：权重与 harness 交替优化。核对位置：§3–4。

**流程：** 固定 harness，以验证成功的采样做模型更新；随后固定新模型，用 Meta-Harness 搜索代码。按预设阶段或停滞信号切换，反复交替。

**边界与启发：** 属于第二阶段参考；最终选择与测试数据使用需单独核查，不能直接继承为本项目独立测试协议。 [原文 2609.00196v1](https://arxiv.org/abs/2609.00196v1)

### 10. When Does Continual Learning Require Learning

类型：比较研究；不列入新进化算法。核对位置：§3。

**流程：** 在持续任务和分布变化下比较参数更新、prompt 优化、上下文经验等适应方式。

**边界与启发：** 有使用进化方法的实验，但论文不是提出一个新的通用 harness 进化循环。 [原文 2607.07847v1](https://arxiv.org/abs/2607.07847v1)

### 11. Harness-Aware Self-Evolving: Co-Evolving Model Weights, Harness, and Task Solutions（HASE）

类型：权重、harness、解答共同进化。核对位置：§3。

**流程：** 把任务求解与 harness 修改纳入统一策略动作，通过 GRPO 训练；候选池经过 PoC 和确定性检查后选择持久更新，再进入下一训练阶段。

**边界与启发：** 局部训练 evaluator 也可被修改，但依赖不可变外部 oracle 约束；本项目固定官方评分器，不采用该修改范围。 [原文 2607.03935v1](https://arxiv.org/abs/2607.03935v1)

### 12. Evolving Agents in the Dark: Retrospective Harness Optimization via Self-Preference（RHO）

类型：无标签离线进化。核对位置：§4。

**流程：** 从历史轨迹按难度、多样性选 coreset；重新求解并自验证、检查一致性，生成改进指令和多个 harness。各候选实际重跑 coreset，模型对新旧轨迹做偏好比较，平均偏好为正才替换。

**边界与启发：** 无标签不等于无评估或无重跑；自偏好并不保证真实正确性。 [原文 2606.05922v3](https://arxiv.org/abs/2606.05922v3)

### 13. HarnessCompass

类型：带归因和泛化约束的离线进化。核对位置：方法部分。

**流程：** 先分别产生不知道结果的执行报告和知道结果的复盘报告，再与真实轨迹核对、聚合。分结构能力和行为指导两条搜索路径，比较候选，尝试修订、重组和精炼，验证后保留。

**边界与启发：** 它的额外步骤主要控制虚假归因、任务特化和补丁落点；不意味着所有项目都需要双轨搜索。 [原文 2608.01918v1](https://arxiv.org/abs/2608.01918v1)

### 14. Adapting the Interface, Not the Model: Runtime Harness Adaptation for Deterministic LLM Agents（Life-Harness）

类型：运行适配与训练集上的层级进化。核对位置：§4。

**流程：** 人工先依据训练失败建立环境契约、skill 检索、动作实现、轨迹调节四层结构；再由 coding agent 根据运行轨迹与指标迭代各层，检查覆盖与回归，冻结后评估。

**边界与启发：** 运行时适配与离线改层要分开；初始结构有人工设计，不是全架构自动发现。 [原文 2605.22166v2](https://arxiv.org/abs/2605.22166v2)

### 15. The Interplay of Harness Design and Post-Training in LLM Agents

类型：设计 / 训练比较；不列入新进化算法。核对位置：§3–4。

**流程：** 控制 harness 设计与后训练设置，比较二者及其交互。

**边界与启发：** 用于解释模型与 harness 收益归因，不提供主要的自动候选搜索循环。 [原文 2606.25447v1](https://arxiv.org/abs/2606.25447v1)

### 16. EvolveNet: Collaborative Harness Evolution for Agent Self-Improvement

类型：多域协作进化。核对位置：§4。

**流程：** 服务器广播共同版本；各域在本地任务上进化并保留共同基线，上传补丁和修复 / 退化证据。服务器区分通用与域内机制，组合后验证，再向各域广播。

**边界与启发：** 解决跨域补丁协作与冲突，不是简单并行生成多个候选再平均。 [原文 2608.04968v1](https://arxiv.org/abs/2608.04968v1)

### 17. DREvo: Distilling Recalibrated Historical Experience for Harness Self-Evolution

类型：历史经验驱动的离线进化。核对位置：Proposed Approach。

**流程：** 用函数级 diff 关联每次运行反馈；根据兼容性、新鲜度和证据一致性重新估计历史经验权重，检索相近失败，从利用、避免、复测、探索等搜索意图中选取方向，生成候选、执行并更新档案。

**边界与启发：** 历史证据会过期；AST 兼容只是代理指标，得分变化也不自动证明某函数修改的因果作用。 [原文 2607.26722v2](https://arxiv.org/abs/2607.26722v2)

### 18. AutoDesign: Meta-Harness Optimization for Long-Horizon Agentic Design

类型：离线多模态设计 harness 进化。核对位置：§3。

**流程：** 内循环设计者与 critic 修订任务产物；外循环分析跨任务轨迹，先规划再编辑，每轮修改一个组件，训练得分严格提高且开发得分不降才接纳，单线保留历史版本。

**边界与启发：** 一个组件可以涉及多个文件。优化评分器与最终评测协议不同，人工干预变体要另记。 [原文 2608.13560v1](https://arxiv.org/abs/2608.13560v1)

### 19. LLMs Improving LLMs: Agentic Discovery for Test-Time Scaling（AutoTTS）

类型：离线推理控制器搜索。核对位置：§3。

**流程：** 先预采样推理分支，构建可回放评价；coding agent 读取历史代码、轨迹与成本曲线，修改测试时控制器，经回放比较后保留搜索记录，最终选控制器与预算参数。

**边界与启发：** 便宜回放依赖受限控制器空间；任意改变 SWE-agent 观察或 prompt 后不能直接重用旧轨迹当新结果。 [原文 2605.08083v2](https://arxiv.org/abs/2605.08083v2)

### 20. EnvHarness: Awakening Static Worlds for Agent Learning

类型：环境进化；不属于本项目内层对象。核对位置：§3。

**流程：** EnvRigger 依据学习者的薄弱点生成可执行环境改动，验证后形成训练阶段或任务环境，反馈用于下一轮环境构建。

**边界与启发：** 改的是训练世界及任务安排，本项目第一阶段将 benchmark 环境固定。 [原文 2608.19880v1](https://arxiv.org/abs/2608.19880v1)

### 21. EvoTrainer: Co-Evolving LLM Policies and Training Harnesses for Autonomous Agentic Reinforcement Learning

类型：训练流程共同进化。核对位置：§3，特别是 §3.5。

**流程：** 收集训练信号、行为和版本证据，诊断后调整奖励、数据、rollout 或训练设置；分支训练比较，保留、剪枝或组合版本，并更新诊断经验。

**边界与启发：** §3.5 对昂贵训练启动和版本晋升 / 剪枝保留人工批准；不能描述成完全无人参与的闭环。 [原文 2606.03108v2](https://arxiv.org/abs/2606.03108v2)

### 22. TTHE: Test-Time Harness Evolution

类型：无标签测试时进化。核对位置：§4。

**流程：** 测试流按批进入；多个分支各自修改父 harness，并参考其他分支轨迹，依靠执行健康、公开测试等代理反馈。无效候选回退；最终 judge 比较分支，可追加探测，选定版本带入下一批。

**边界与启发：** 当前批已参与适配，且报告选中输出；这不是冻结 harness 后只在未来未见任务测迁移。 [原文 2607.08124v1](https://arxiv.org/abs/2607.08124v1)

### 23. HarnessForge: Joint Harness and Policy Evolution for Adaptive Agent Systems

类型：harness / policy 种群共同进化。核对位置：§3。

**流程：** 对 harness—policy 配对种群归因失败，生成候选，逐级扩大评价任务并用 Pareto 筛选；幸存候选的成功轨迹用于 SFT / LoRA，继承后继续进化。

**边界与启发：** 其外部改进模型和被训练模型可不同，不能当成 A＝B 的冻结模型 baseline。 [原文 2606.01779v1](https://arxiv.org/abs/2606.01779v1)

### 24. VeRO: A Harness for Agents to Optimize Agents

类型：优化器评测基础设施。核对位置：§3。

**流程：** 提供查看数据 / 实验、编辑代码、固定提交身份、隔离评估及预算管理，支持 inspect → edit → evaluate → keep / revert 的实验。

**边界与启发：** 不强制一种进化算法；值得复用的是实验可检查性。注意早期标题不同。 [原文 2602.22480v4](https://arxiv.org/abs/2602.22480v4)

### 25. Workspace Optimization: How to Train Your Agent（DreamTeam）

类型：外部 workspace 适应。核对位置：§2、§4。

**流程：** 冻结模型的多个角色维护观察器、模拟器与策略等外部产物；先预测再行动，利用实际状态偏差与互审修复相应产物，并回归检查已有转移。

**边界与启发：** 主要是任务内世界模型与工作区学习，和跨任务冻结后迁移的目标需要区分。 [原文 2605.09650v1](https://arxiv.org/abs/2605.09650v1)

### 26. Phantom Guardrails: When Self-Improving Agent Harnesses Fix Failures That Never Happened

类型：诊断风险实证；不列入新优化器。核对位置：§3–4。

**流程：** 在受控确定性环境中检验自改进者是否给没有发生的失败增加限制。

**边界与启发：** 支持保留证据引用、允许无修改，并核对修改是否对应真实机制；不支持无限增加模型审查角色。 [原文 2607.13083v1](https://arxiv.org/abs/2607.13083v1)

### 27. Verify Smarter, Evolve Further: Efficient Harness Evolution through Behavior-Aware Verification（HarnessLens）

类型：行为感知分级验证。核对位置：§4。

**流程：** 从轨迹抽取并核对经验，选择当前父版本的一个提案；轻量加载检查后，在相关任务及回归组匹配重跑。检查行为变化，再在偏重新任务组的确认集合上比较；必要时修订重验。

**边界与启发：** 重点是把昂贵执行预算用在相关行为与确认上；机制证据和最终分数分开记录。 [原文 2608.27311v1](https://arxiv.org/abs/2608.27311v1)

### 28. Recursive Harness Self-Improvement（RHI）

类型：任务级递归适配。核对位置：§3、Algorithm 1。

**流程：** 为当前任务生成角色、信息交换与工作流 harness；每轮新运行，与缓存的上一轮产物做模型成对评价，依据历史再修改，改善比例不足时停止。

**边界与启发：** 这里的 recursive 不代表外层 optimizer 源码也在自改；任务级增益不等于跨任务泛化。 [原文 2607.15524v1](https://arxiv.org/abs/2607.15524v1)

### 29. COMFYCLAW: Self-Evolving Skill Harnesses for Image Generation Workflows

类型：视觉工作流与 skill 进化。核对位置：§3。

**流程：** 内层编辑类型化工作流、渲染并依据区域 / 需求视觉反馈修复；外层聚类成功失败，创建、修改、合并或删除 skill。为相应簇生成新验证提示，比较新旧 skill 的 verifier 奖励后接纳。

**边界与启发：** 合成验证提示仍与生成修改的簇有关；不能直接当成独立真实分布测试。 [原文 2607.01709v1](https://arxiv.org/abs/2607.01709v1)

### 30. Towards Direct Evaluation of Harness Optimizers via Priority Ranking

类型：优化器评估；不列入新进化算法。核对位置：§3–5。

**流程：** 构造人工标注的场景和组件优先级，直接检查优化器能否把修改注意力放到正确组件。

**边界与启发：** 可补充诊断质量评价，但优先级答对不能替代补丁运行与未见任务效果。 [原文 2605.22505v1](https://arxiv.org/abs/2605.22505v1)

### 31. Stop Comparing LLM Agents Without Disclosing the Harness

类型：立场 / 评测规范；不列入新进化算法。核对位置：§1–3及作者项目页。

**流程：** 主张披露 harness，采用固定 harness 或因子实验，避免把框架差异误认成模型差异。

**边界与启发：** 不是自进化流程；其关于 harness 影响大小的主张也不是所有任务上的普遍定律。 [原文 2605.23950v1](https://arxiv.org/abs/2605.23950v1)

## 4. 目前真正收敛的部分，以及没有收敛的部分

以下是本次对上述方法的归纳，主要针对冻结权重的离线进化，不强行覆盖训练环境进化等旁支。

```text
当前 harness + 开发任务
          ↓
执行，保留轨迹、结果与成本
          ↓
从证据提出机制假设，生成可执行修改
          ↓
候选执行与比较
          ↓
保留 / 回退，保存版本和经验
          └────────→ 下一轮
```

共通的是把经验沉淀到模型外可重复执行的结构，而不只修好眼前的答案；让运行反馈进入修改过程；以执行结果筛选修改。历史经验逐渐从一段摘要发展成可检索源码、逐任务轨迹与补丁档案。部分方法还专门处理经验过期、错误归因和验证成本。

尚未收敛的问题包括：

- **搜索拓扑**：单当前版本、候选池、beam、树搜索、多域分支并存。
- **修改粒度**：单 prompt、单函数、单组件、整个 harness 都有；“一个可解释机制”不等于“一行代码”。
- **反馈来源**：官方 verifier、代理规则、模型偏好、视觉 judge、人工反馈并存，可信度不能混同。
- **接纳规则**：严格提高、无退化、Pareto、偏好为正或验证奖励不降，都有采用；没有通用阈值。
- **证据形态**：固定摘要与主动检索并存；多模态中还存在“先看图再给文本梯度”的中间层。
- **推广目标**：当前任务、后续批次、同分布新任务、跨域 / 跨模型是不同主张。

因此，不能从“许多文章使用反思”推导反思有效，也不能从某个重框架的分数推导每一层检查都有必要。需要针对组件的消融和匹配预算比较。

补充一篇不在清单中的反证线索：[Rethinking the Evaluation of Harness Evolution for Agents，2607.12227v1，§3–4](https://arxiv.org/abs/2607.12227v1)。它在 Terminal-Bench 2.1 的具体比较中发现 harness evolution 没有稳定超过简单测试时搜索，迁移也有限。其实现与任务范围不能否定所有进化方法，但提醒我们：额外反馈、额外采样和同任务反复选择都可能产生表面收益。本项目已有的重试对照、独立测试和搜索成本记录应保留。

## 5. 对多模态研究主张的影响

SHAPER、COMFYCLAW 和 AutoDesign 已经把视觉反馈接入某种外层改进。因而“看图片后修改 harness”本身不足以界定贡献，A＝B 也不是独有设定。

本项目更值得检验的链条是：

```text
原始视觉证据的访问
    → 是否纠正仅文本 / 摘要中的诊断偏差
    → 是否改变所选择或实现的运行机制
    → 机制是否在新 rollout 中触发
    → 是否在未见任务上改善原生得分，以及付出多少成本
```

这是待验证假设。不能把“请求含图片”当成模型正确理解，也不能把分数提高直接归因为某张图片。

三组对照仍合理：T 为日志；S 为日志加视觉诊断摘要；R 为相同日志、相同摘要加原图查询权限。A 的视觉能力保持相同。摘要生成成本、原图检索成本和失败搜索成本都计入；如果 R 从未查图，应按实际使用解释。可记录少量人工核对的诊断事实，辅助解释补丁来源，不必为所有候选再加一个判官模型。

对于 Claw-Eval-MM、Vision2Web 和 SWE-MM，还需先确认哪些失败确实有可诊断的视觉证据，以及官方指标能否反映该失败。媒体多不等于进化空间大；评分不敏感的视觉改善只能作为辅助机制证据，不能悄悄换评分口径。

## 6. 结合当前代码，建议讨论的最小流程

这是建议，不是本轮已确认或已实现的方法。

1. **固定当前 H 和任务协议。** A 跑一批探索任务，保留成败案例；可复用身份一致的结果，但新采样单独记。
2. **一个 B 会话查证并修改。** 首屏提供概览、当前源码入口、反馈与证据索引；B 按需查事件、图片和历史补丁，同会话完成诊断与编辑。预算用尽或证据不足允许无修改。
3. **少量独立候选。** 可从每轮一个候选开始，再以相同搜索预算比较两个；每次围绕一个可解释机制，可跨多个必要文件。数量不是论文结论。
4. **最低必要有效性检查。** 补丁能应用、候选确实加载、入口可运行；不为可逆代码编辑堆砌模型审查。
5. **执行比较决定去留。** 先在相关探索案例小规模重跑并观察声称的行为；值得继续的候选进入固定开发验证，比较得分、回归和成本。边界候选是否复测以及接纳阈值待定。
6. **归档继续，冻结后测试。** 同时保存未接纳原因、实际行为和成本；下一轮可检索。最终独立测试不用于本轮选优。

机制未触发、触发无益、实现失败和环境失败要分开记录，但不必立刻为每种状态建立复杂硬门禁。先检查它们是否影响真实候选判断。

不建议第一版同时引入多分支组合、双路径归因、多个 critic、历史经验复杂加权和训练。它们各有合理动机，但应在出现对应瓶颈后比较。单一修改者的价值首先是成本和可解释性，而非已经证明它最优。
